# VPS Control Room — Best-Practice Audit

> _Generated 2026-06-14 by a multi-agent best-practice audit (5 area auditors → adversarial verification of every high/critical finding → synthesis). Reflects the tree at the session-fix commit. Overall **78/100**, no criticals._
>
> **Already remediated in the same change set** (see commits): the session/terminal-restore fixes — 3-day expiry + sliding renewal, JSON 401 on `/api/*` (the `Method Not Allowed` restore crash), fresh-cwd history restore — and **H1** below: device revocation now bites every request (`middleware.ts` + `require-session.ts` re-check the device allowlist), so a revoked/stolen token can no longer be kept alive by sliding renewal. The remaining findings are open follow-ups.

## 1. Executive Summary

The VPS Control Room is a well-engineered single-user host-control panel. The security and auth foundations are genuinely strong for the threat model: HMAC-SHA256 signed cookies with timing-safe verification, a fail-closed boot guard that refuses to start under a short/missing secret, two-factor login (password + pre-approved device) with global and per-IP rate limiting, a gateway bearer that decouples from the login password, loopback-only agent bind by default, secret scrubbing from spawned ptys, and symlink-safe fs roots. Frontend hygiene is high (complete `error.tsx` coverage, correct hooks discipline, disciplined `response.ok` guarding). The architecture is correctly layered with a single shared contracts source.

The weaknesses cluster in two places: **session lifecycle/state** (stateless tokens that survive device revocation; in-memory-only terminals that vanish on agent restart) and **deploy verification/observability** (promote checks only `systemctl is-active`, never that the build serves HTTP; no smoke test; env-doc drift). Several "high" findings were correctly downranked by adversarial review because systemd's default cgroup kill or operator-driven manual deploys neutralize the claimed impact.

**Weighted overall score: 78 / 100.** (Security 82 ×0.30, Frontend 82 ×0.15, Host Agent 74 ×0.20, Architecture & Performance 78 ×0.20, Deploy & Ops 74 ×0.15 → 78.0.)

### Top 5 to fix first
1. **Device revocation does not invalidate live sessions** (`frontend/src/shared/auth/session.ts:62`) — the only confirmed-high security finding; revoking a compromised device is a no-op until the token expires, and sliding renewal can extend it indefinitely.
2. **Terminal sessions are in-memory-only** (`agent/src/terminal/manager.ts:69`) — any agent restart/reboot/crash silently destroys all live AI-agent panes and scrollback; "Restore" only re-spawns blank shells.
3. **Frontend promote verifies only `is-active`, never HTTP** (`scripts/deploy.sh:108`) — a boot-but-serve-500 build is promoted and the known-good `.next-previous` is deleted.
4. **EventSource error handler leaks the stream** (`frontend/src/features/terminals/hooks/use-pane-terminal.ts:540`) — orphaned native EventSource keeps reconnecting after pane unmount, leaking route-handler streams and upstream WS connections.
5. **Inconsistent defense-in-depth `requireSession()`** across agent-proxy routes (`stream`, `buffer`, `log`, `patrol/pending`, `alfa/watchers`) — defeats the codebase's own stated second auth layer on its highest-value routes.

## 3. Findings by Severity

### Critical
None.

### High

#### H1. Device revocation does not invalidate already-issued sessions
- **File:** `frontend/src/shared/auth/session.ts:62` (also `frontend/src/shared/auth/require-session.ts:14`, `frontend/middleware.ts:67`, `agent/src/terminal/auth.ts:97`, `frontend/src/shared/auth/device-store.ts:99`)
- **Problem:** Sessions are stateless HMAC tokens validated only on signature + `expires_at`. The cookie carries `device_id`, but no verify path re-checks `isApproved(device_id)` — `isApproved()` is invoked in exactly one place, the login route. `revokeDevice()` only removes the allowlist entry and mutates no session state, so a cookie issued to a now-revoked device stays valid until natural expiry. Worse than reported: middleware sliding renewal (`middleware.ts:25-49`) re-issues the cookie with a fresh full-length expiry on activity while preserving `device_id`, so an actively-used stolen token can survive revocation indefinitely. Sessions grant full host shell/exec/fs/docker control.
- **Fix:** After HMAC+expiry succeed on privileged paths (`require-session.ts` and the agent WS/HTTP auth), assert `payload.device_id` is still approved; cheapest correct version is `isApproved(payload.device_id)` in `requireSession.ts`, or bump a per-device/global session epoch in `revokeDevice` and compare it.
- **Confidence:** high. **Adversarial verdict: REAL, severity confirmed high.**

#### H2. Terminal sessions are in-memory-only; agent restart destroys all ptys and scrollback
- **File:** `agent/src/terminal/manager.ts:69` (also `agent/src/app/bootstrap.ts:87-102`, `scripts/install-systemd.sh:55-92`, `frontend/.../sessions/storage.ts`)
- **Problem:** `TerminalManager` stores sessions in a plain in-process `Map` with no serialization; `shutdown()` never persists. The agent unit uses default `KillMode=control-group`, so any agent-affecting deploy, reboot, crash, or explicit restart SIGKILLs the whole cgroup and every pty child dies. Frontend history persists only the spec, so "Restore" re-spawns a fresh blank shell — the running process and scrollback are unrecoverable. The same codebase already has a disk-persistence pattern (`agent/src/cron/manager.ts:185`) that was deliberately not applied here. (One overstatement: not *every* `deploy.sh main` triggers this — frontend-only deploys don't restart the agent.)
- **Fix:** Either explicitly surface ephemerality ("sessions will be lost on deploy"), or decouple pty lifetime via tmux/abduco/dtach/detached supervisor with reattach-on-boot from a small on-disk id→pid registry. At minimum persist the session metadata `Map` to `~/.openclaw` so restart can truthfully show what was running.
- **Confidence:** high. **Adversarial verdict: REAL, severity confirmed high** (genuine, surprising data loss for the product's core use case; capped at high because it is availability/UX, not security/correctness).

#### H3. Frontend promote verifies only `systemctl is-active`, never that the build serves HTTP
- **File:** `scripts/deploy.sh:108` (also `:109` rollback delete, `:256` agent restart, `scripts/install-systemd.sh:28`)
- **Problem:** `activate_frontend_build()` swaps `.next`, `systemctl start`, then `is-active --quiet`. With `Type=simple`, the unit is active the instant the process execs — even if Next serves 500s on every request. On success the script immediately `rm -rf "${PREVIOUS_NEXT_DIR}"`, deleting the known-good build and defeating the blue-green rollback this function exists for. The agent restart has the identical gap.
- **Fix:** After `systemctl start`, poll `curl -fsS http://127.0.0.1:4000/api/version` (already returns `buildId`) for ~30s before deleting `PREVIOUS_NEXT_DIR`; on failure run the existing rollback branch. Probe `/health` on 4001 for the agent.
- **Confidence:** high. **Adversarial verdict: REAL, downranked high → medium** (deploy is operator-driven `workflow_dispatch` with a human watching; a typecheck/lint preflight at `deploy.sh:204-209` catches many bad builds; the solidly-uncatchable case is "boots fine, serves 500s").

#### H4. EventSource error handler nulls the ref but never closes it — native auto-reconnect leaks the stream after unmount
- **File:** `frontend/src/features/terminals/hooks/use-pane-terminal.ts:540` (handler 540-554; cleanup 580; stream route `frontend/app/api/terminals/[id]/stream/route.ts:51`)
- **Problem:** The SSE `error` listener unconditionally sets `eventSourceRef.current = null` before any branch, never calls `eventSource.close()`, and never calls `connect()`. The stream route calls `controller.close()` on every upstream WS drop, which ends the event stream normally — the browser's native EventSource treats that as recoverable and auto-reconnects on its retry timer. Because the ref was nulled, the unmount cleanup (`eventSourceRef.current?.close()`) is a no-op, so the orphaned EventSource reconnects to `/api/terminals/[id]/stream` forever after the pane is closed, each reconnect spawning a fresh route-handler stream + upstream WS to the agent. `reconnectAttemptsRef` is incremented but never compared to a max or used for backoff.
- **Fix:** Decide intent *before* nulling the ref: if not reconnecting, call `eventSource.close()`; if reconnecting, keep the ref pointing at the live object so unmount cleanup works (or close-then-schedule a guarded `connect()`). Use `reconnectAttemptsRef` for exponential backoff / max-attempts disconnect.
- **Confidence:** high. **Adversarial verdict: REAL, downranked high → medium** (genuine unbounded connection leak, but single-user, loopback-bound; blast radius is one browser + one local agent and it requires the drop-then-close sequence).

#### Investigated, not confirmed (verdict.isReal = false)

- **Graceful shutdown never kills spawned ptys — "orphans every shell on restart"** (`agent/src/app/bootstrap.ts:87`). The code observation (no `shutdownAll()`, `shutdown()` doesn't iterate sessions) is accurate, but the load-bearing impact claim is false: the systemd unit (`scripts/install-systemd.sh:55-92`) is `Type=simple` with **no `KillMode` override**, so the default `control-group` SIGTERM-then-SIGKILLs every pty in the agent cgroup on `systemctl restart` (deploy.sh:256). Ptys are reaped, not orphaned, and the cited "NO persistence across restart invariant" doesn't exist in the repo docs. **Residual (low):** adding `terminalManager.shutdownAll()` is reasonable portability/defense-in-depth in case the unit ever moves to `KillMode=process` or runs outside systemd. Treat as Low, not High.

### Medium

#### M1. Agent re-implements `verifySession` without the frontend's fail-closed weak-key floor
- **File:** `agent/src/terminal/auth.ts:21` (cf. `frontend/src/shared/auth/session.ts:42`)
- **Problem:** The agent's verifier is a copy of the frontend's but omits the `if (!secret || secret.length < MIN_SECRET_LEN) return null;` guard. Not exploitable today because `config.assertConfigSecrets` (`agent/src/config.ts:56`) refuses to boot under a <32-char secret, but the duplicated primitive has drifted — any future loosening of the boot guard silently re-enables forgeable cookies on the WS auth path.
- **Fix:** Share one `verifySession` across frontend+agent, or add the identical `MIN_SECRET_LEN` guard at `agent/src/terminal/auth.ts:22`. **Confidence:** high.

#### M2. Several agent-proxy route handlers omit the in-handler `requireSession()` used by siblings
- **File:** `frontend/app/api/terminals/[id]/stream/route.ts:23` (also `terminals/[id]/buffer/route.ts:11`, `skills/route.ts:7`, `log/route.ts:7,20`, `patrol/pending/route.ts:7` + ack, `alfa/watchers/route.ts:16,21`)
- **Problem:** `require-session.ts` documents the helper as deliberate defense-in-depth "so a middleware bypass can't reach the host-control proxy," yet the highest-value routes (live stream, buffer scrollback, `log` DELETE/cleanup, alfa watchers) skip it and rely solely on middleware. Not a live bypass (middleware still gates them), but a matcher regression or misconfig would expose privileged proxies while protected siblings stay safe. The stream route re-auths at the agent WS; `alfa/watchers` and `log` hit the agent over the gateway secret with no per-request session proof.
- **Fix:** Add `const denied = await requireSession(); if (denied) return denied;` to the top of every agent-proxy handler uniformly. **Confidence:** high. *(Reported across both Frontend and Security/Architecture areas as L/M; treated here as Medium for the privileged subset.)*

#### M3. SSE stream route does not re-verify the session cookie in-route
- **File:** `frontend/app/api/terminals/[id]/stream/route.ts:23`
- **Problem:** Every other terminal route calls `requireSession()`; the SSE GET handler — the longest-lived, highest-value connection (live pty output) — omits it and relies on middleware + agent-side WS cookie verification. A middleware bypass would expose live pty output here while POST/DELETE routes stay protected. (Same root cause as M2; called out separately for the stream specifically.)
- **Fix:** Add the `requireSession()` gate at the top of GET before opening the upstream WS; the agent WS check remains the real boundary. **Confidence:** high.

#### M4. `evictForNewSession` silently kills an idle-but-running pane with no client notification
- **File:** `agent/src/terminal/manager.ts:337` (kill path `:308`)
- **Problem:** At the 16-session cap with no exited session, eviction kills the running session with the smallest `updated_at`. But `updated_at` only advances on output/input/resize, so a busy-but-quiet build or agent looks "most idle" and gets killed mid-work. `closeSession()` kills the pty but broadcasts no `status`/`evicted` event — the user's open pane vanishes with only a server log line.
- **Fix:** Broadcast a terminal event (`{type:'status', reason:'evicted'}`) to the victim's subscribers before killing; weight eviction toward sessions with **zero subscribers** rather than smallest `updated_at`. **Confidence:** high.

#### M5. Unbounded concurrent `pstree` forks under session-list polling
- **File:** `agent/src/terminal/manager.ts:38` (callers `:78`, `:91`)
- **Problem:** `listSessions()` calls `refreshInnerAgent()` per running session, each `execFile`-ing `pstree -p <pid>` when its 15s cache is stale. There's a per-session in-flight guard but **no global cap**: with 16 running sessions and frequent `/terminals` GET + authed `/health` polling, a cold-cache window can fork up to 16 concurrent `pstree` per poll cycle — the exact fork pressure the patrol `LOAD_GATE` (`scheduler.ts:30`) defends against, but absent here.
- **Fix:** Bound with a small global semaphore (max 2-3 in-flight forks), or move inner-agent detection onto one shared interval that batches all running pids. **Confidence:** medium.

#### M6. WebSocket upgrade performs no Origin check (CSWSH defense-in-depth gap)
- **File:** `agent/src/terminal/gateway/socket.ts:38`
- **Problem:** `handleTerminalSocketUpgrade` authorizes the `/ws/terminals` upgrade solely via the signed session cookie; it validates path and `sessionId` but never inspects `Origin`. Browsers attach cookies to cross-origin WS upgrades and can connect to localhost, so if the session cookie isn't strictly SameSite, a malicious page could drive a live pty. Loopback bind + cookie signing reduce but don't eliminate this.
- **Fix:** Reject upgrades whose `Origin` isn't in an allowlist (`NEXT_PUBLIC_APP_URL` / configured tailnet origin) before `handleUpgrade`; pair with `SameSite=Strict` on the session cookie. **Confidence:** medium.

#### M7. CLAUDE.md / .env.example document the wrong var for the frontend→agent reach address
- **File:** `frontend/src/features/terminals/server/terminal-gateway.ts:1`
- **Problem:** All frontend API routes reach the agent via `terminalGatewayFetch`, which reads `process.env.TERMINAL_GATEWAY_URL || 'http://127.0.0.1:4001'`. But CLAUDE.md (lines 22, 55-56) and `.env.example` tell operators to set `CONTROL_ROOM_HOST` / `AGENT_HEALTH_PORT` for the frontend — neither of which the frontend reads. `TERMINAL_GATEWAY_URL` is absent from `.env.example`. An operator moving the agent off-default would silently break every terminal/fs/cron/patrol call while `/api/health` still passes against the wrong target.
- **Fix:** Add `TERMINAL_GATEWAY_URL` to `.env.example` (default `http://127.0.0.1:4001`) and correct CLAUDE.md; drop/clarify the misleading `CONTROL_ROOM_HOST`/`AGENT_HEALTH_PORT`-for-frontend entries. **Confidence:** high.

#### M8. Deploy-critical `CONTROL_ROOM_DOMAIN` is undocumented and fails silently to an empty Traefik Host rule
- **File:** `scripts/deploy.sh:248` (template requirement `:133`)
- **Problem:** The Traefik template keys every router on `Host(\`${CONTROL_ROOM_DOMAIN}\`)`, rendered via `envsubst` with `${CONTROL_ROOM_DOMAIN:-}`. The var is in no doc, and the `:-` default sidesteps `set -u`, so an operator who never set it gets `Host(\`\`)` written to the live Traefik config with no error — silently breaking ingress instead of failing the deploy.
- **Fix:** Document `CONTROL_ROOM_DOMAIN`; in deploy.sh drop the `:-` default and add an explicit fail-fast guard before tee-ing into the live Traefik config. **Confidence:** high.

#### M9. No post-deploy smoke test anywhere in the pipeline
- **File:** `scripts/deploy.sh:264`
- **Problem:** `deploy.sh` ends at "Deployment complete" with zero HTTP verification of either service (grep for curl/wget/health returns nothing). Combined with H3's is-active-only check, a deploy completes green while the dashboard is down, with no alert path (failures only land in journald).
- **Fix:** Final stage that curls `/api/version` (frontend) and `/health` (agent), asserts returned `buildId == BUILD_ID_SHORT`, exits non-zero on mismatch. Optionally notify on failure. **Confidence:** high.

No sliding/idle expiry — fixed 24h absolute lifetime only** (`frontend/app/api/auth/login/route.ts:157`). `expires_at` set once and never refreshed at login; a captured cookie is usable for the full window and a legitimate user is hard-logged-out mid-session at 24h. - **L3. Defense-in-depth `requireSession()` omitted on patrol/alfa/buffer routes** (`frontend/app/api/terminals/[id]/buffer/route.ts:11`, etc.) — frontend-area framing of M2; same fix. Confidence high.
- **L4. Initial terminal-session load calls `response.json()` without checking `response.ok`** (`frontend/src/features/terminals/hooks/use-terminal-sessions.ts:133`). On a 401/redirect/HTML body it throws into a generic "Failed to load" message; sibling poll (`:209-211`) and mutations guard correctly. Add an `if (!response.ok)` branch before `.json()`. Confidence high.
- **L5. Exited-session cleanup timer never `.unref()`'d (and WS heartbeat interval likewise)** (`agent/src/terminal/manager.ts:368`; heartbeat `socket.ts:116`). A pending 30-min TTL keeps the event loop referenced, unlike the unref'd daily timer at `bootstrap.ts:72`. Call `.unref()` after the `setTimeout`. Confidence high.
- **L6. `getBuffer` materializes and returns the full 250KB buffer even when only tail lines are requested** (`agent/src/terminal/manager.ts:234`; consumer `gateway/http.ts:199`). Every buffer request allocates+discards the full string and split-array. Add a lines-only method or split lazily. Confidence high.
- **L7. YOLO / `--dangerously-skip-permissions` launch has no server-side confirmation beyond the shared gateway secret** (`agent/src/terminal/profiles.ts:231`). Any caller holding the gateway secret can spawn an unsandboxed autonomous agent; the spawn audit entry (`manager.ts:160`) doesn't flag the YOLO flag. Acceptable under single-user trust, but record `dangerouslyAllow` in the audit log and consider a narrower capability/re-confirm. Confidence medium.
- **L8. Upload collision suffix can still clobber an existing file** (`agent/src/terminal/gateway/http.ts:181`). Fallback name `${stem}-${body.length}${ext}` collides on same name + same size; `fs.writeFile` has no exclusive flag. Use a uuid suffix or `O_EXCL` with retry. Confidence high.
- **L9. Health endpoint uses `listSessions()` (spawns `pstree` per session) just to count panes** (`agent/src/app/health-server.ts:60`). Use `peekSessions().length` or a cheap `sessionCount()` getter — health is the most-polled endpoint. Confidence high.
- **L10. Redundant 5s session-list polling duplicates the SSE status channel** (`frontend/src/features/terminals/hooks/use-terminal-sessions.ts:200`). SSE already delivers per-session status; on top of it run four independent pollers (sessions 5s, alfa 6s, patrol 8s, devices 8s), each `/terminals` GET re-running per-session pstree/proc work. Emit `session-added`/`session-removed` lifecycle events on the existing channel and drop the list poll to a 30s/visibility safety-net. Confidence high.
- **L11. Pane tree is not memoized; every poll tick re-renders all panes via unstable props** (`frontend/src/features/terminals/components/terminals-main.tsx:179`; `terminal-pane.tsx:24`). `TerminalPane` isn't `React.memo`; `liveIds`/`restorable`/`paneRoleAndColor` rebuilt each render. Heavy xterm work is ref-isolated so DOM cost is bounded, but reconciliation walks every pane. Wrap in `React.memo` + `useMemo` the derived structures. Confidence medium.
- **L12. `TERMINAL_ONLY_MODE` gates Convex deploy + `convex/.env.local` requirement but is undocumented** (`scripts/deploy.sh:137`). Default `true` silently never deploys Convex even after `convex/` changes; appears in no doc. Document it (and its default) in `.env.example` / CLAUDE.md. Confidence high.
- **L13. Static-snapshot restore re-injects deleted chunk hashes into every new build, growing `.next/static` unboundedly** (`scripts/deploy.sh:219`). Each deploy's served static set is the union of the last 3+ builds (all `max-age=31536000`); cleanup never prunes the live `.next/static`. Restore only the most-recent 1 snapshot, or periodically rebuild static from scratch. Confidence medium.
- **L14. systemd services use `Type=simple` + `Restart=always` with no readiness/watchdog** (`scripts/install-systemd.sh:28`, agent `:67`). A hung-but-alive process (stalled loop, listener never bound) is never restarted. Add `WatchdogSec` + `sd_notify` from the health loop, or a timer that curls both endpoints and restarts on failure. Confidence medium.

## 4. Cross-Cutting Themes

1. **Stateless auth vs. revocable identity.** The system's strongest design choice (stateless HMAC tokens, no session DB) is also the root of its top security finding (H1) and a Low (L1): there is no way to invalidate a live credential out-of-band. The device-approval second factor is checked only at login, never at request time. Any revocation, global-logout, or idle-timeout feature requires re-introducing a small piece of server-side session state (a device-approval re-check or a per-device/global epoch).

2. **In-process state coupled to process lifetime.** Terminals (H2), exited-session timers (L5), and inner-agent caches all live only in the agent process and die with it. The codebase already proved it can persist (cron `persist()`), but the highest-value state — live terminals — was left ephemeral. Decide explicitly: accept-and-surface ephemerality, or persist/reattach.

3. **Self-declared defense-in-depth applied inconsistently.** The repo documents two invariants — in-handler `requireSession()` on every privileged proxy, and a single source of truth for the HMAC verifier — and then violates both: the verifier is copied and drifted (M1), and `requireSession()` is missing on the stream/buffer/log/patrol/alfa routes (M2/M3/L3). The protection exists; it just isn't uniform. These are low-effort to bring into line.

4. **Deploy proves the process started, not that the product works.** `is-active`-only promotion (H3), no smoke test (M9), and pid-only systemd liveness (L14) all share one gap: nothing in the pipeline ever issues an HTTP request to confirm the new build serves. The endpoints to probe (`/api/version`, `/health`) already exist.

5. **Documentation drift on operationally-load-bearing env vars.** `TERMINAL_GATEWAY_URL` (M7), `CONTROL_ROOM_DOMAIN` (M8), and `TERMINAL_ONLY_MODE` (L12) are all undocumented and all fail silently (wrong target, empty Host rule, skipped Convex deploy) rather than loudly. The fix is the same class of change: document + fail-fast.

6. **Fork/poll pressure on an 8-vCPU box.** Per-session `pstree` forks fan out from both `listSessions` polling (M5) and the health endpoint (L9), and four overlapping client pollers (L10) keep re-triggering that work — duplicating the `LOAD_GATE` concern the patrol scheduler already solved elsewhere.

## 5. Prioritized Remediation Roadmap

### Quick wins (≤1 hour each, low risk, high ratio)
- **H1 (partial):** Add `isApproved(payload.device_id)` to `requireSession.ts` and the agent WS auth — closes the revocation gap with a single store lookup.
- **M2 / M3 / L3:** Add the `requireSession()` one-liner to stream/buffer/skills/log/patrol-pending/alfa-watchers handlers (restores stated defense-in-depth).
- **M1:** Add the `MIN_SECRET_LEN` guard to `agent/src/terminal/auth.ts:22` (or import the shared verifier).
- **M9 + H3 (partial):** Append a curl `/api/version` + `/health` smoke step at `deploy.sh:264` asserting `buildId`, and gate the `.next-previous` delete (`deploy.sh:109`) behind that probe.
- **M7 / M8 / L12:** Add `TERMINAL_GATEWAY_URL`, `CONTROL_ROOM_DOMAIN`, `TERMINAL_ONLY_MODE` to `.env.example` + CLAUDE.md; drop the `:-` default and fail-fast on empty `CONTROL_ROOM_DOMAIN`.
- **L4, L5, L8, L9:** `response.ok` guard before `.json()`; `.unref()` the cleanup timer; uuid/`O_EXCL` upload suffix; `peekSessions().length` in health.
- **Info:** Fix or rename `deployedAt` in `/api/version`.

### Medium effort (a few hours, some design)
- **H4:** Rework the EventSource error handler — decide intent before nulling the ref, call `close()` when not reconnecting, keep the live ref otherwise, add backoff/max-attempts via `reconnectAttemptsRef`.
- **M4:** Broadcast an `evicted` status event and re-weight eviction toward zero-subscriber sessions.
- **M5 / L9 / L10:** Introduce a global `pstree` semaphore (or a single batched inner-agent interval), and emit `session-added/removed` lifecycle events on the existing SSE channel to retire the 5s list poll (slow it to 30s/visibility).
- **M6:** Origin allowlist on the WS upgrade + `SameSite=Strict` cookie.
- **L1:** Implement sliding/idle expiry coherently with the existing middleware renewal (resolve the H1/L1 interaction at the same time).
- **L14:** systemd `WatchdogSec` + `sd_notify` (or a health-check timer unit).
- **L11:** `React.memo` + `useMemo` for the pane tree.

### Larger efforts (design + ownership decision)
- **H2:** Decide and implement the terminal-persistence strategy — detach/reattach via tmux/dtach/supervisor with an on-disk id→pid registry, or formally accept ephemerality and surface a "sessions lost on deploy" warning + truthful "what was running" from persisted metadata. This is the single biggest UX/availability investment and unblocks the product's core long-lived-agent value proposition.
- **L13:** Bound `.next/static` growth (restore only the latest snapshot, or periodic clean rebuild) and document the rollout/disk tradeoff.
- **L7:** If the trust model ever broadens beyond single-user, gate the YOLO/`--dangerously-skip-permissions` launch behind a distinct capability + audit-flag; at minimum record `dangerouslyAllow` in the spawn audit entry now.
